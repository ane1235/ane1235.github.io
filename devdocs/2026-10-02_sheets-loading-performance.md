# 근무표 로딩 개선

기준: `f9d312a`의 `/sheets/`. 사용자가 선택한 조건은 조회 시 최신 데이터 유지다.

## 확인한 원인과 변경

- 평일 첫 화면은 목록 1회, Assign 2회, Duty 1회로 API를 4회 호출했다. Assign 화면과 Duty의 근무 변경 반영이 같은 Assign 탭을 동시에 요청했기 때문이다. 진행 중인 동일 읽기 요청을 공유해 총 3회로 줄였다. 목록 조회 뒤 데이터 조회를 시작하는 두 단계 구조는 유지된다.
- 응답 완료·실패 시 공유 요청을 제거한다. 기존의 무기한 페이지 내부 근무 데이터 캐시를 제거하고 API 요청에 `cache: 'no-store'`를 지정했다. 날짜 재선택과 새로고침 때 최신 데이터를 읽는다. 열어 둔 화면에 대한 자동 갱신은 추가하지 않았다.
- CSS·JS의 매번 바뀌는 `Date.now()` 주소를 배포 버전 `20261002.1`로 바꿨다. 여섯 JS는 기존 순서대로 `defer`로 실행한다. 변경 없는 정적 파일은 브라우저 캐시를 재사용할 수 있으며, 근무 데이터에는 이 캐시를 적용하지 않는다. 이후 CSS/JS 수정 배포 시 HTML의 해당 버전을 함께 올려야 한다.
- Apps Script는 데이터 조회 시 전체 탭을 순회하지 않고 `getSheetById()`로 선택한다. Assign 조회만 `includeFontColors=false`를 보내 불필요한 색상 조회·전송을 생략한다. 기본 API 응답과 Duty의 휴일 판정용 글자색, 날짜·시간 표시값은 유지한다.

서버 캐시, 브라우저 저장소의 근무 데이터 캐시, 로그인 결과 캐시는 추가하지 않았다. 동일 월 안에서 날짜를 바꿀 때도 다시 조회하므로 기존 메모리 캐시보다 대기가 생길 수 있다. 이는 최신 조회 조건에 따른 변경이다.

## 검증

```bash
node --test tests/sheets-loading.test.cjs
git diff --check
```

- 11개 검사 통과: 요청 공유·분리, 재조회 시 변경 반영, 네트워크/HTTP/JSON/업무 오류 후 재시도, 로그인 요청 분리, 대시보드 요청 수, 백엔드 색상·시간·행 대응 및 기존 기본값.
- Chromium에서 합성 시트 응답으로 변경 전후 대시보드 HTML 일치 확인. 첫 화면 API 4회 → 3회, 날짜 재선택과 새로고침 때 변경 반영, JavaScript 오류 없음 확인.
- 브라우저 검사의 외부 API와 CDN은 모의 응답을 사용했다. 운영 사이트 및 `script.google.com`은 이 클라우드 네트워크에서 403으로 차단되어 실제 Apps Script 실행 시간, 전송량, 운영 로딩 시간 단축은 측정하지 못했다. 요청 수 감소를 로딩 시간 25% 감소로 해석해서는 안 된다.

## 실제 반영 순서

1. `scripts/SheetViewerService.gs` 변경을 기존 Apps Script 프로젝트에 반영하고 기존 웹 앱 배포를 새 버전으로 갱신한다. 실행 계정·접근 권한·URL은 기존 설정을 유지한다. GitHub push만으로 Apps Script 코드는 갱신되지 않는다.
2. 프런트엔드 변경을 검토해 GitHub Pages 배포 브랜치에 반영한다. 새 프런트엔드는 구버전 백엔드도 사용할 수 있다. 이 경우 색상 생략 최적화만 적용되지 않는다.
3. 로그인 상태에서 평일 날짜를 열고 개발자 도구 Network로 목록 1회 + Assign 1회 + Duty 1회를 확인한다. 시트 수정 후 날짜 재선택/새로고침으로 값과 휴일·퇴근시간 표시를 확인한다.
4. 동일 장치·네트워크·날짜에서 처음 방문과 재방문을 구분하여 여러 번 측정한다. Apps Script 자체의 실행 시작·리다이렉트와 목록→데이터의 두 단계 대기는 남아 있다. 필요하면 다음 단계로 최신 데이터를 한 요청에 반환하는 초기 조회 API를 검토한다.

위 검증 결과는 로컬 코드와 모의 응답에 대한 결과다. GitHub Pages 게시 상태와 Apps Script 배포 버전은 각각 별도로 확인해야 한다.
