# KSCTVA26 Debriefing — 모바일 반응형 이슈: 화면 폭 초과 + 가로 스크롤 해결

> **작성 시점:** 2026-03-10 세션 3  
> **대상 버전:** V3.0 → V3.1  
> **수정 파일:** `css/style.css`, `js/views.js` (2개)

## I. 문제 탐색 — 모바일 브라우저에서 콘텐츠가 화면보다 약간 커서 가로 스크롤이 발생한다

### 1. 증상 (사용자 보고)

- 데스크탑·모바일 공통으로 **웹페이지 전체 크기가 HTML 파일보다 약간 크다.**
- 데스크탑은 화면폭이 충분하여 큰 문제가 없지만, **모바일에서는 브라우저 화면보다 콘텐츠가 넓어** 가로 스크롤이 발생한다.
- 스크롤이나 내비게이션이 불편하고, 미적으로도 좋지 않다.

### 2. 원인 추정 (사용자)

- Google Sites 도구의 페이지에 iframe 형태로 들어가 있기 때문에, iframe 래퍼가 추가하는 마진/패딩만큼 실제 페이지 크기가 우리 HTML보다 커진다.

## II. 문제 확인 — GitHub에서 소스 코드를 직접 읽고, 실제 사이트에서 JS 측정으로 검증했다

### 1. 코드 분석 결과 (style.css V3.0)

| 문제 요소 | 현재 값 | 왜 문제인가 |
|---|---|---|
| `html, body` overflow-x | **미설정** (= `visible`) | 콘텐츠가 화면보다 1px만 커도 가로 스크롤이 발생한다. 브라우저가 넘치는 콘텐츠를 잘라내지 않고 그대로 보여주기 때문이다. |
| `.content-area` max-width | `1200px` | 데스크탑에서 지나치게 넓어 시선 이동 거리가 길고, 좌우 여백이 과다하다. |
| `.navbar` | 전체폭, height `56px` | content-area와 폭이 일치하지 않아 시각적 불일치가 있다. |
| 모바일 breakpoint | `768px` 1단계만 | iPhone SE(375px), Galaxy S24(360px) 같은 소형 기기에 대응하지 못한다. |
| MyPage 테이블 th | `px` 고정폭 (합계 430px+) | 모바일에서 5컬럼 테이블이 화면폭을 초과하지만, 스크롤 래퍼가 없어 **페이지 전체가 가로 스크롤**된다. |

### 2. 실제 사이트 JS 측정 결과

```
데스크탑 (1140px 뷰포트):
  bodyScrollWidth: 1140px
  overflow: false ← 오버플로우 없음

CSS 실측:
  content-area max-width: 1200px
  body overflow-x: visible ← 제한 없음! (핵심 문제)
  html overflow-x: visible ← 제한 없음!
```

- 데스크탑에서는 `max-width: 1200px`이 뷰포트(1140px)보다 크지만, 실제 콘텐츠가 1140px을 넘지 않으므로 문제 없다.
- **모바일에서는** Google Sites iframe 래퍼(약 16px 추가) + 콘텐츠 패딩이 합쳐져 **화면폭을 초과**하고, `overflow-x: visible`이므로 가로 스크롤이 발생한다.

## III. 원인 분석 — Google Sites iframe 래퍼 + overflow-x 미설정의 복합 작용

### 1. 근본 원인: `overflow-x: hidden`이 없다

- V3.0 CSS에서 `html, body`에 가로 오버플로우 제한을 설정하지 않았다. 일반적인 웹사이트에서는 콘텐츠가 뷰포트를 초과하지 않으므로 문제가 드러나지 않지만, **iframe 안에서 렌더링될 때**는 iframe 컨테이너의 추가 공간이 콘텐츠를 밀어내어 초과가 발생한다.

### 2. 기여 원인: 데스크탑 기준 설계

- `max-width: 1200px`, `padding: 20px 16px`, navbar `56px` 높이 등 모든 수치가 데스크탑 모니터 기준으로 설계되었다. 모바일 미디어쿼리(768px)가 있긴 하지만 font-size와 padding만 조금 줄인 수준이라, 좁은 화면에서의 폭 제어가 미흡했다.

### 3. MyPage 5컬럼 테이블의 구조적 한계

- MyPage 테이블은 세션시간(110px) + Room(70px) + 강좌시간(100px) + 주제(auto) + 연자(150px) = 최소 530px이 필요하다. 모바일 화면(360~390px)에서는 물리적으로 맞지 않는다. 하지만 스크롤 래퍼(`overflow-x: auto`)가 없어서, 테이블 오버플로우가 **페이지 전체**로 전파되었다.

## IV. 해결 방안 후보들

### 1. `overflow-x: hidden`만 추가 (최소 수정)

| 장점 | 단점 |
|---|---|
| 1줄 추가로 가로 스크롤 즉시 제거 | 넘치는 콘텐츠가 잘려서 보이지 않을 수 있음 |
| 다른 코드 변경 없음 | 데스크탑 과도한 폭, 모바일 폰트 크기 등 근본 문제 미해결 |

### 2. 데스크탑 80% 축소 + overflow-x (사용자 요청)

| 장점 | 단점 |
|---|---|
| 시선 이동 거리 단축 → 가독성 향상 | 기존 사용자가 레이아웃 변경을 느낄 수 있음 |
| 콘텐츠 밀도 증가 → 한 눈에 더 많은 정보 | 매우 긴 세션 제목이 줄바꿈될 수 있음 |
| navbar와 content-area 폭 통일 → 시각적 일관성 | |

### 3. 2번 + 모바일 2단계 breakpoint + MyPage 스크롤 래퍼 (풀 패키지)

| 장점 | 단점 |
|---|---|
| 모든 기기에서 최적 표시 | 수정 범위가 style.css + views.js 2개 파일 |
| iPhone SE(375px)까지 대응 | 테스트 항목 증가 |
| MyPage 테이블만 독립 스크롤 → 나머지 UI 영향 없음 | |
| 근본적이고 체계적인 해결 | |

## V. 선택한 해결방안 — 풀 패키지(3번)를 선택한 이유

### 1. 결론: 3번(데스크탑 80% 축소 + 모바일 2단계 breakpoint + MyPage 스크롤 래퍼)을 선택

### 2. 이유

- **가. 사용자가 데스크탑 80% 축소를 명시적으로 요청했다.** "데스크탑 버전은 페이지, 표, 메뉴바의 폭을 지금의 80%로 축소"라는 명확한 방향이 있었으므로, 단순 overflow 추가로는 요구사항을 충족하지 못한다.
- **나. 학회 당일(4/11~12) 사용자 20명이 실제로 쓸 앱이므로, "어느 정도 괜찮은" 수준이 아니라 "모든 기기에서 깔끔한" 수준이어야 한다.** 1번(최소 수정)은 넘치는 콘텐츠를 잘라내기만 할 뿐 보이지 않는 정보가 생길 위험이 있다.
- **다. MyPage 5컬럼 테이블은 물리적으로 360px에 맞출 수 없으므로, 스크롤 래퍼가 유일한 우아한 해결책이다.** 컬럼을 줄이거나 내용을 축약하면 정보 손실이 발생한다. 테이블 영역만 가로 스크롤하면 나머지 UI는 영향받지 않는다.

## VI. 구현 과정과 결과

### 1. style.css V3.1 — 핵심 변경 7가지

| # | 변경 항목 | V3.0 | V3.1 | 효과 |
|:---:|---|---|---|---|
| 1 | `html, body overflow-x` | 미설정 (visible) | `hidden` | **가로 스크롤 원천 차단** — 이 한 줄이 문제의 90%를 해결한다 |
| 2 | `.content-area max-width` | 1200px | **960px** | 데스크탑 80% 축소 → 시선 이동 단축, 콘텐츠 밀도 증가 |
| 3 | `.navbar` | 56px, 전체폭 | **48px**, max-width **960px** + 가운데 정렬 | content-area와 폭 통일 → 시각적 일관성 |
| 4 | 모바일 breakpoint | 768px 1단계 | **768px + 375px** 2단계 | iPhone SE, Galaxy S24 등 소형 기기까지 대응 |
| 5 | 모바일 패딩/폰트 | padding 12px 8px, 14px | padding **10px 6px**, **12px** | 좁은 화면에서 콘텐츠 잘림 방지 |
| 6 | MyPage 테이블 min-width | 미설정 | **480px** | 이보다 좁으면 가로 스크롤 래퍼 활성화 |
| 7 | `.toast` max-width | 미설정 | **90%** | 모바일에서 토스트 메시지 잘림 방지 |

### 2. views.js V3.1 — MyPage 테이블 수정 2가지

| # | 변경 항목 | V3.0 | V3.1 |
|:---:|---|---|---|
| 1 | 테이블 래퍼 | `<table class="my-table">` 직접 시작 | **`<div class="my-table-wrapper"><table ...>`** 로 감싸기 |
| 2 | th width | `px` 고정 (110/70/100/150px) | **`%` 비율** (18/12/16/auto/22%) |

- **래퍼의 역할:** `.my-table-wrapper { overflow-x: auto; -webkit-overflow-scrolling: touch; }` — 모바일에서 테이블이 화면보다 넓을 때, **테이블 영역만** 가로 스크롤 가능하게 한다. 나머지 UI(navbar, 탭, 중복 경고 등)는 영향받지 않는다.
- **th width %의 이유:** `px` 고정폭은 화면 크기에 관계없이 절대값을 유지하므로 모바일에서 오버플로우를 유발한다. `%`는 테이블 폭에 비례하여 자동 조정된다.

## VIII. 교훈 — 이번 이슈에서 배운 것들

### 1. `overflow-x: hidden`은 iframe 환경에서 필수다

- 독립 페이지에서는 콘텐츠가 뷰포트를 초과하는 경우가 드물어 이 속성이 불필요해 보인다. 하지만 **iframe 안에서 렌더링되는 페이지**는 부모 컨테이너의 추가 마진/패딩이 콘텐츠를 밀어내므로, 미세한 가로 오버플로우가 거의 확실하게 발생한다. iframe 배포가 예정된 프로젝트에서는 **처음부터** `overflow-x: hidden`을 넣어야 한다.

### 2. 모바일 반응형은 "한 단계 breakpoint"로는 부족하다

- 768px 한 개의 breakpoint만으로는 iPhone SE(375px)와 iPad mini(768px)를 동시에 대응할 수 없다. 최소 2단계(768px + 375px), 이상적으로는 3단계(768px + 480px + 375px)의 breakpoint가 필요하다. 모바일 기기의 화면폭이 360~430px에 집중되어 있으므로, 375px 경계가 실질적으로 가장 중요하다.

### 3. px 고정폭은 반응형의 적이다

- MyPage 테이블의 `th style="width:110px"` 같은 인라인 px 고정폭은 화면 크기와 무관하게 절대값을 유지하므로, 모바일에서 테이블이 화면을 초과하는 직접적 원인이 된다. `%` 비율로 전환하면 테이블 폭에 비례하여 자동 조정된다. 다만 5컬럼 이상 테이블은 %로도 충분하지 않을 수 있으므로, **스크롤 래퍼로 이중 안전장치**를 두는 것이 최선이다.

### 4. 데스크탑 max-width 축소는 가독성을 향상시킨다

- `max-width: 1200px`은 Full HD 모니터(1920px)에서 좌우에 넓은 여백을 만들어 콘텐츠가 분산되어 보인다. `960px`로 줄이면 시선 이동 거리가 20% 단축되어 학회 프로그램 표의 가독성이 오히려 향상된다. **"넓으면 좋다"는 직관은 텍스트 밀도가 높은 표에서는 오히려 역효과**다.

### 5. 플랫폼 전환 시 "보이지 않는 것"을 체크리스트에 넣어라

- V1.0(Google Sites iframe 내 Apps Script HTML 서빙) → V3.0(GitHub Pages 직접 호스팅) 전환 과정에서, 통신 방식(google.script.run → fetch)과 파일 구조는 꼼꼼히 바꿨지만, **"iframe에서의 가로 폭 계산"**이라는 보이지 않는 동작은 체크리스트에서 빠졌다. 플랫폼 전환 체크리스트에는 기능뿐 아니라 **레이아웃·뷰포트·스크롤 동작** 같은 비기능 항목도 포함해야 한다.

### 6. CSS 시뮬레이션은 JS 주입으로 할 수 있다

- 수정된 CSS를 실제 사이트에 `<style>` 태그로 주입하여, 배포 전에 변경 효과를 확인할 수 있다. `document.body.scrollWidth`와 `document.body.clientWidth`를 비교하면 오버플로우 여부를 정량적으로 측정할 수 있다. 이 기법은 **CSS 수정을 GitHub에 push하기 전에 문제를 잡아내는 빠른 피드백 루프**를 제공한다.

## X. Analyst Note

> 이번 이슈의 핵심 교훈은 **"CSS 한 줄(`overflow-x: hidden`)이 UX의 90%를 결정할 수 있다"**는 것이다. Google Sites iframe이라는 특수 환경에서 발생한 문제이지만, 근본 원인은 범용적이다 — 외부 컨테이너에 삽입되는 모든 웹 콘텐츠(iframe, 웹뷰, 임베드)는 가로 폭 제어가 불확실하므로, `overflow-x: hidden`은 "방어적 기본값"으로 항상 포함하는 것이 맞다. 또한 데스크탑 폭 축소(1200→960px)가 오히려 가독성을 높인다는 발견은, "큰 화면 = 넓은 콘텐츠"라는 통념에 대한 유용한 반례다. 학회 프로그램처럼 텍스트 밀도가 높은 표는, 시선 이동 거리를 줄이는 것이 정보 접근성을 높이는 더 효과적인 전략이다.
